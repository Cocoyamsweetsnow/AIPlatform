# 架构选型决策清单

> 用法：每个决策点列了**选项 / 权衡 / 我的推荐 / 什么时候该换**。
> 最后一节是「待拍板」表格——你填完告诉我，我按你的选择改代码。
> 已经做出的决策会沉淀成 ADR，放在 `docs/adr/` 下（模板见文末）。

---

## 一、三档推荐组合（先对号入座）

| | 内部工具（< 50 人） | 对外产品（SaaS） | 私有化交付（政企） |
|---|---|---|---|
| HTTP 框架 | cpp-httplib（现状） | Drogon 或 uWebSockets | Drogon |
| 数据库 | SQLite 或 PostgreSQL | PostgreSQL 16 | PostgreSQL（客户机房） |
| 缓存 | 进程内 | Redis | Redis |
| 部署 | 单机 docker compose | 2+ 副本 + Nginx | docker compose + 离线包 |
| 前端 | 复用 Open WebUI | 自研 Next.js | 复用 + 白标 |
| 模型 | 云端 API | 云端 API + 降级 | 本地 llama.cpp / vLLM |
| 鉴权 | 静态 API Key | 自建 JWT | OIDC / LDAP |

**我的默认推荐**（如果你没有特殊约束）：**内部工具那一列 → 先用 2~4 周把业务跑通 → 用户量起来后再按表格往右迁移**。
迁移成本被刻意压低了：`llm/` 与 `chat/` 层不依赖 HTTP 框架和数据库实现，换框架只改 `http/server.cpp`，换库只加一个仓储实现。

## 二、决策点

### D1. HTTP 服务框架（影响最大）

| 选项 | 优点 | 代价 | 适合 |
|---|---|---|---|
| **A. cpp-httplib（现状）** | 单头文件、零依赖、2 分钟上手 | 每连接一线程，**并发流上限 = 线程池大小**（当前 64） | 内部工具、演示、< 100 并发流 |
| **B. Drogon** | 多 reactor + C++20 协程、自带 ORM/WebSocket、生产级 | 依赖多（jsoncpp/uuid/openssl/zlib），首次编译 10+ 分钟 | 对外产品、需要 WebSocket |
| **C. uWebSockets** | 吞吐和内存最优 | API 偏底层、文档少、生态小 | 海量长连接、团队有经验 |
| **D. Boost.Beast** | 完全可控、可定制协议细节 | 心智负担最大，容易写出 bug | 有特殊协议需求 |

**推荐 A → 并发压测超过 100 路流再换 B。** 切换成本约 400 行（`src/http/server.cpp`），业务层不用动。

> **2026-11-02 更新**：负责人选择**提前切 B**，POC 通过（200 路 SSE / 300 路空闲连接实测，
> 见 [POC-DROGON.md](POC-DROGON.md) 第 5 节），**主线迁移已落地**
> （`src/http/server_drogon.cpp`，httplib 保留为 `-DAIPLATFORM_HTTP=httplib` 回退项）。
> Drogon 要求 ≥ 1.9.14。落地实测与遗留问题见 [adr/0001](adr/0001-http-framework.md) 文末。

### D2. 数据库

| 选项 | 优点 | 代价 | 适合 |
|---|---|---|---|
| **A. PostgreSQL 16** | JSONB、**pgvector**（RAG 免装向量库）、分区、并发写强 | 运维比 MySQL 稍重 | 默认推荐 |
| **B. MySQL 8** | 团队熟悉、运维成熟（这台机器上就有 MySQL） | 无 pgvector，RAG 要另上 Milvus/Qdrant | 已有 DBA 体系 |
| **C. SQLite** | 零运维、单文件、备份就是拷文件 | 单写者，多副本要换 | 内部小工具 |

**推荐 A。** 如果你们已有 MySQL 运维团队，选 B 也完全合理——只是 RAG 阶段要额外规划向量库。

### D3. 数据访问层

| 选项 | 说明 |
|---|---|
| **A. libpqxx + 手写 SQL（推荐）** | SQL 完全透明，执行计划可调，迁移工具友好 |
| B. Drogon ORM | 只在 D1 选 B 时考虑；省事但 SQL 被框架接管 |
| C. sqlpp17 | 编译期检查 SQL，但模板报错极难读 |

### D4. 缓存与限流

| 选项 | 优点 | 代价 |
|---|---|---|
| **A. 进程内（现状）** | 零依赖、纳秒级 | 多副本时限额不共享、重启丢失 |
| **B. Redis** | 跨进程精确限流、会话热数据、Pub/Sub | 多一个要运维的组件 |

**推荐：单机 A；一旦上多副本，D4 必须切 B**（否则配额会被放大 N 倍）。

### D5. 部署形态

| 选项 | 优点 | 代价 |
|---|---|---|
| **A. 单机 docker compose + Nginx（推荐起步）** | 一台机器、回滚 = 换镜像 tag | 单点故障 |
| B. Kubernetes | 弹性、滚动更新、多环境 | 需要 SRE，学习曲线陡 |
| C. systemd 裸机 | 最简单、无容器开销 | 环境漂移 |

### D6. 前端

| 选项 | 优点 | 代价 |
|---|---|---|
| **A. 复用 Open WebUI / LobeChat（推荐先做）** | 1 天可用，功能比自研全 | 品牌不可控、定制受限 |
| B. Next.js 自研 | 完全可控 | 2 周起，且要持续维护 |
| C. 单页 HTML + fetch 流式 | 半天，够演示 | 功能很少 |

**推荐：先用 A 跑两周收集真实反馈，再决定要不要 B。** 我们的接口是 OpenAI 兼容的，A 只需要改一个 base URL。

**当前落地（2026-11-03）：方案 C 的增强版，未改变上面的推荐。**
仓库内置了一个零构建单页 UI（`web/`，构建期嵌入二进制）：流式对话、Markdown / 代码块、
本地会话、明暗主题、Token 设置、移动端布局。它解决的是「演示、联调和无网络环境」，
不是生产前端——**没有登录 / 多租户 / 云端会话同步**。生产仍按 A（复用）或 B（自研）
由人拍板；接口保持 OpenAI 兼容，A/B 都能直接接。

| | 方案 C 内置页 | 方案 A 复用 Open WebUI |
|---|---|---|
| 部署依赖 | 无（随二进制） | 额外部署一个前端服务 |
| 定制 / 品牌 | 完全可控（但是单文件原生 JS） | 受上游限制 |
| 登录 / 多租户 | 无 | 有（需对接） |
| 适用阶段 | 演示、联调、内网工具 | 对外产品 |

### D7. 模型接入

| 选项 | 优点 | 代价 |
|---|---|---|
| **A. 纯云端 API（推荐起步）** | 零运维、模型最强 | 数据出境、按量计费、依赖网络 |
| B. 云端 + 本地混合 | 敏感数据走本地，断网可用 | 要 GPU、要维护推理服务 |
| C. 纯本地 | 数据不出内网 | 效果受模型规模限制 |

Provider 接口已经为 B/C 留好位置：写一个 `llama_provider.cpp` 即可，上层不用改。

### D8. 鉴权

| 选项 | 适用 |
|---|---|
| **A. 自建 JWT + Argon2id** | 对外产品，2~3 天 |
| B. Keycloak / OIDC | 企业客户、需要 SSO/多因素 |
| **C. 静态 API Key（现状）** | 内部工具，半小时 |

### D9. 依赖管理

| 选项 | 说明 |
|---|---|
| **A. third_party/ 单头文件（现状）** | 零网络、构建快、可审计；依赖一多就难管 |
| B. vcpkg manifest | 版本锁定、跨平台；首次构建慢 |
| C. Conan 2 | 更灵活、支持私有仓库；学习成本高 |

**推荐：A 保持到 D1 换成 Drogon（或依赖超过 10 个）为止，然后转 B。**

### D10. 可观测性

| 选项 | 说明 |
|---|---|
| **A. spdlog + `/metrics` 文本端点（推荐）** | 轻量，Prometheus 直接能抓 |
| B. OpenTelemetry | 全链路追踪，多服务时才有必要 |

### D11. 单体还是微服务

**现在：单体。** 一个人维护时，微服务的每个好处（独立部署、独立扩容）都用不上，坏处（分布式调试、网络延迟、运维复杂度）却全都要付。等团队超过 10 人、或某个模块确实需要独立扩容（比如推理服务）时再拆。

## 四、决策记录（ADR）模板

每个「不可逆或代价高」的决策写一条，放 `docs/adr/NNNN-短标题.md`：

```markdown
# 0003 使用 PostgreSQL 作为主数据库

- 状态：已接受
- 日期：2026-11-02
- 决策者：xxx

## 背景
需要持久化会话与消息，并计划做 RAG。

## 考虑过的方案
1. PostgreSQL（pgvector 直接可用）
2. MySQL 8（团队熟悉）
3. SQLite（内网小工具）

## 决定
选择 1。

## 后果
- 正面：RAG 不需要额外向量库；分区和索引能力强
- 负面：需要 DBA 维护；备份策略要单独设计
- 触发重新评估的条件：如果团队完全没有 PG 运维能力
```
